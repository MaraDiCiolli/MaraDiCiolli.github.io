On the art of writing documentation nobody asked for

Why I started writing docs before writing code — and how it changed the way I think about software design entirely.

Read →

There's a particular kind of clarity that comes from trying to explain something before you've built it. I started writing README files for projects that didn't exist yet — not as a productivity hack, but because I kept finding that the act of writing surfaced assumptions I didn't know I was making.

When you write "this library lets you do X," you're forced to reckon with whether X is actually what someone needs. More often than not, I'd rewrite the doc three or four times, each revision pulling the design in a slightly different direction, before I ever touched a code editor.

The practice has made me a slower starter but a faster finisher. I throw away fewer prototypes. And the docs, when the project finally ships, are already done — because they were the blueprint all along.

Three books that rewired how I think about systems

A short list of non-technical books that taught me more about engineering than any textbook.

Read →

Thinking in Systems by Donella Meadows was the first book that made me realize feedback loops aren't just a software concept — they're everywhere, from economics to ecology. Once you see them, you can't unsee them.

How Buildings Learn by Stewart Brand changed how I think about software architecture. Brand argues that the best buildings are the ones designed to be changed. The same is true for codebases. Design for adaptation, not permanence.

Seeing Like a State by James C. Scott is a masterclass in understanding why top-down systems fail. Every time I see an over-engineered abstraction layer, I think about Scott's critique of "high modernism" — the belief that legibility from above is more important than functionality on the ground.

My terminal setup, late 2025 edition

Every year or so I rethink my dev environment. Here's where things landed this time around.

Read →

I've been a tmux holdout for years, but I finally switched to Zellij and haven't looked back. The layout system is more intuitive, the defaults are sane, and the plugin ecosystem has matured enough that I don't miss my old tmux config.

For the editor, I'm still on Neovim — but running it inside a purpose-built Nix flake that pins every dependency. No more "works on my machine" when I move between my laptop and desktop. The whole environment reproduces in under a minute.

The biggest quality-of-life improvement, though, was the simplest: I started using a dedicated scratchpad terminal that auto-saves everything I type into timestamped markdown files. It's just a shell alias and a pipe to tee, but having a searchable log of every command and note from the day has been invaluable.

Nov 15, 2025 Open Source

Maintaining a project nobody stars but everyone uses

On the strange life of infrastructure software — downloaded millions of times, mass-ignored on GitHub.

Read →

I maintain a small utility library that processes config files. It has 47 stars on GitHub and, according to npm, about 2 million weekly downloads. These two numbers tell very different stories about what "success" means in open source.

Nobody gets excited about config parsing. Nobody tweets about it. But when it breaks, I hear about it within minutes — because it's buried four or five levels deep in dependency trees that power tools people actually do care about.

The experience has taught me that the most important software is often the most invisible. And that maintaining it is less about heroic feature work and more about the quiet discipline of not breaking things — of being boring, reliably.
